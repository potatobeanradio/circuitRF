## 0. What this brief delivers

Four things, and only four:

1. **References**: hand-written solver inputs and their outputs, committed under
   `testdata/em3d/f0/`. They are the externally generated data that briefs 7 and 9 are gated
   against (overview §1h), and they are useful to planar MoM and kernel W even if nothing else is
   built.
2. **Answers to named questions** (§3). Each is a sentence with evidence, not an impression.
3. **The validated-version list** each backend brief pins (§4).
4. **A recommendation on F1 vs F1b first** (D4), with the evidence behind it.

**Nothing under `src/` changes.** A spike that leaves product code behind has made a design decision
nobody reviewed.

## 1. `R-em3d1-1` — who does what

Some of this can be done in a headless session on the owner's Mac. Some needs other machines, and
some needs data only the owner has. The split is decided up front so that no part is silently
skipped.

| Part | Who | Why |
|---|---|---|
| Install Gmsh, openEMS, Palace on macOS (arm64); run both cases through both solvers; write the references and the report | **agent, on the owner's Mac** | a shell is enough |
| Install each solver **three times from clean** on Windows (openEMS, Gmsh natively; Palace in the Linux subsystem) and on Linux (x64) | **owner**, following the log format of §5 | no Windows or Linux box is reachable from this session |
| A default foot length and ball size (§6.6, D2) | **owner**, from assembly data | cannot be derived; the note says "checked against assembly data, not assumed" |

**`R-em3d1-1a`** The report states, per part, whether it was done and by whom. A part not done is
listed as **not done**, never omitted.

**`R-em3d1-1b`** Installs on the Mac are done the way a user would do them: Homebrew where a
formula exists (Gmsh), upstream's own documented route otherwise (openEMS's build or its release
archive; Palace through Spack, as its documentation says). Record the exact commands. **Do not
work around a failure by patching upstream.** A failure and what fixed it is itself the data §7.2's
known-failures table is seeded from.

**`R-em3d1-1c`** A Palace build via Spack is expected to take hours. Run it in the background with
its full log kept. If it fails, record the failing step verbatim and try the one obvious remedy
(a missing build tool, a retry after a transient mirror failure). A second failure is a finding to
report, not a problem to solve in this brief.

## 2. `R-em3d1-2` — the two cases

Both are small enough that each solver run takes **seconds to a minute** on a laptop (the
standing practice: keep EM runs short). Both are written **by hand**: a `.geo` script and a Palace
JSON for FEM, a CSXCAD XML for FDTD. **They are not generated by circuitRF**, which has no generator
yet, and must not be regenerated by one later (overview §1h).

**The spike may use upstream's own scripting interfaces** (openEMS's Python interface to write the
CSXCAD XML and its lumped ports; Gmsh's own tools) because the spike is not circuitRF code. The
output is then generated by the solver authors' own code, which makes it a *better* structural
oracle for briefs 7 and 9 than a hand-typed file. Commit the script that produced each input beside
it, under `testdata/em3d/f0/…/source/`, clearly marked as spike material, and **never** reference
it from `src/` (§5.2 forbids product code from using those interfaces; brief 6's firewall test
scans `src/` and `tools/`, not `testdata/`).

### Case A — one bond wire over ground (§10 F0; kernel W's regression anchor)

- 1 mil (25.4 µm) gold wire, σ₂₀ = 4.10×10⁷ S/m, **evaluated at 20 °C** for every solver including
  kernel W (overview §1c). Kernel W's `.wBond` sets `OperatingTempC = 20` for this case.
- Two 100 × 100 µm pads, 1.0 mm apart centre to centre, on a 100 µm substrate (εr = 9.8,
  tanδ = 0) over a ground plane; loop height 150 µm by wBond's definition. Record the assembly-
  definition height too (§6.6).
- A lumped port from each pad to ground, 50 Ω. 1–40 GHz, 40 points.
- **Run it three ways in Palace**: round cross-section; the perimeter-matched hexagon of §6.6
  (side = πd/6, flat bottom); the hexagon with a wedge foot of 2d at each end. **Run it once in
  openEMS**, as a thin wire at the grid resolution. This is the case §4.3 expects FDTD to struggle
  with, and the point is to measure how badly.

### Case B — a microstrip-to-microstrip via transition

- Stackup: top copper, 0.2 mm dielectric (εr = 3.66, tanδ = 0.004), a ground plane with a round
  antipad, 0.2 mm dielectric, bottom copper. Copper 35 µm, σ = 5.8×10⁷ S/m.
- A 50 Ω microstrip on top, a plated round via (0.3 mm drill, 0.6 mm pad, 0.9 mm antipad) through
  the ground plane, and a 50 Ω inverted microstrip on the bottom, both referenced to the middle
  plane. 5 mm of line each side. Lumped ports at the line ends. 0.1–20 GHz.
- This is the case §4.3 expects FDTD to be good at, apart from the round barrel. It is also solvable
  by circuitRF's planar MoM with vias (L9), so it gives a three-way comparison.

**`R-em3d1-2a`** For each case and solver, also run the **circuitRF solver it corresponds to**
(kernel W for A, planar MoM for B) through the ordinary `.cem`/`.wBond` route, and commit that
setup beside the references.

**`R-em3d1-2b`** For each run, record: mesh or cell count, peak memory, wall time, and for
Palace the adaptive iterations used; for openEMS the time steps and the end criterion reached.

## 3. `R-em3d1-3` — the questions, each answered with evidence

Each answer goes in the report, with the command or file that shows it.

| # | Question | Needed by |
|---|---|---|
| Q1 | **Agreement.** Case A: \|S21\| and the series inductance Im(Z₁₂…)/ω extracted from each run (state the extraction). Case B: \|S11\|, \|S21\|, phase of S21. Report the spread between Palace, openEMS and the circuitRF solver, per decade of frequency. | 7, 9, 10 |
| Q2 | **FDTD on the bond wire.** How many cells did openEMS need to get within 0.1 dB of Palace on \|S21\| at 10 GHz, and what did that cost in time and memory? | D4, and §4.3's guidance text |
| Q3 | **Hexagon vs round** (§6.6). The resistance difference from corner crowding, at 1, 10 and 40 GHz, against the round wire of equal perimeter. The note says to measure it, not assume it small. | 4 |
| Q4 | **The foot.** How much does a 2d wedge foot change \|S21\| and L at 10 GHz? If it is below the solver's own convergence spread, the foot's default barely matters and D2 is a formality. | 4, D2 |
| Q5 | **Gmsh provenance from `.geo`** (overview §1e). Can a `.geo` script, with no API, recover which fragment output came from which input? Try overview §1e's recipe (conductors as voids, disjoint dielectrics, `Geometry.OCCBooleanPreserveNumbering`, tight `BoundingBox` selection, a `Printf` entity table). **Answer: works / works with caveats (list them) / does not work.** | 7 |
| Q6 | **Palace conductor model.** Does a conductor modelled as a void with a finite-conductivity boundary give the same answer as a meshed conductor on case A, within Palace's own adaptive tolerance? And a trace as a zero-thickness sheet with a `Thickness` on case B? | 7 |
| Q7 | **openEMS probe timing** (overview §1f). Show, from the pinned version's own probe files, the time offset between a voltage and a current probe at one port. | 9 |
| Q8 | **CSXCAD triangle import** (§6.5). Does the pinned openEMS read an STL or PLY polyhedron? One tiny test. | 9 (future Tier B) |
| Q9 | **Palace capability probe** (§7.1). What does the pinned Palace say about itself: a version flag, a build-info output, anything naming its eigensolver? If nothing, what is the cheapest probe run that fails fast without one? | 6 |
| Q10 | **Palace config schema.** Where does the pinned version keep its embedded JSON schema, and can it be extracted to a file to test a writer against? | 6, 7 |
| Q11 | **openEMS output formats.** The probe file format (columns, header lines), and what the executable prints and returns on success, on an XML error and on an unmet end criterion. | 9 |
| Q12 | **Install cost** on each platform tried: time, disk, failures met and what fixed each (§5's log). | the next series |

## 4. `R-em3d1-4` — the validated versions

**`R-em3d1-4a`** The report names **one** version of each of Palace, Gmsh and openEMS that the
references were produced with. That is the validated list briefs 6, 7 and 9 start from. One entry
each: every entry is a writer to keep and a validation set to re-run (§5.3).

**`R-em3d1-4b`** Re-survey first. The note's version table (its header) is dated 2026-09-24 and says
to re-check before relying on it. If a newer Palace or openEMS has shipped, use it and say so.

```
    B-via/
        palace/  openems/  planar/  ...
docs/design/em-3d-f0-findings.md    the report: §1a's done/not-done table, Q1-Q12, the D4 recommendation
```

**`R-em3d1-5a`** Keep outputs small. Commit port data, not field dumps or meshes. If a file is over
~1 MB, say why in the README or leave it out.

**`R-em3d1-5b`** No personal paths, usernames or machine names in any committed file. Solver logs
routinely contain `/Users/<name>/…`; anonymise them to the path's shape (the standing rule). A
`grep` for the home directory and the username over `testdata/em3d/` is part of the gate.

**`R-em3d1-5c`** The install log format, for the owner's Windows/Linux runs to follow:
*platform · tool · version · route · start/end time · disk used · result · the failing step's output
verbatim · what fixed it*. One row per attempt, including the ones that worked.

## 6. Gate

This brief has no tests; its gate is a review of the report.

1. `docs/design/em-3d-f0-findings.md` answers Q1–Q12 with evidence, or says **not done** and why.
2. Both cases have Palace, openEMS and circuitRF-solver outputs committed, or the missing one is
   named with its reason.
3. §5b's grep finds nothing.
4. `git status` shows nothing under `src/` or `tests/`.
5. The report ends with the D4 recommendation and a proposed validated-version list.
6. **The note is updated only where F0 has refuted it.** For example, if §1e's recipe fails, §6.2's
   provenance sentence changes. It is a dated rev-5 line in the note's changelog, not a rewrite.

## 7. Scope

- **No product code, no tests, no generator.**
- **No circuitRF-generated solver input** anywhere in `testdata/em3d/`.
- **No install assistant work.** §5's log is its raw material, nothing more.
